# 校园办事小秘书实施方案

> **执行说明：** 本方案面向三人学生团队，按照“小范围做完整、每周有可演示成果、先验证再扩展”的原则编制。任务使用复选框，完成一项勾选一项。

**编制日期：** 2026年9月15日  
**项目类型：** 华为ICT大赛创新赛“创新应用”方向候选项目  
**团队规模：** 3名学生  
**暂定名称：** 校园办事小秘书——基于AgentArts与可信知识库的高校事务智能服务平台

---

## 一、项目概述

### 1. 项目背景

高校办事信息通常分散在学校官网、教务处、学生工作处、学院网站、微信公众号、班级群和线下通知中。学生在办理学生证补办、校园卡补办、请假、宿舍报修、奖助学金申请、转专业和毕业手续时，常遇到以下问题：

1. 不知道应该去哪个部门或网站查询；
2. 搜索到的通知可能已经过期；
3. 通知篇幅较长，难以快速提取办理条件和材料；
4. 同一事务可能因校区、学院、年级和学生类型不同而变化；
5. 普通大模型可能生成看起来合理、实际上并不存在的流程；
6. 学生获得政策解释后，仍不知道下一步具体该做什么。

本项目计划建设一个校园事务智能体。系统先从经过整理和审核的校园知识库中检索依据，再生成结构化办事指南，并展示来源、发布日期、适用范围和风险提示。在没有可靠依据时，系统应当明确说明不确定，而不是自行编造答案。

### 2. 项目目标

- 理解学生使用自然语言提出的办事问题；
- 识别学生准备办理的具体事项；
- 从可信校园知识库中检索有关规定；
- 信息不足时主动询问最关键的补充信息；
- 输出办理条件、材料、步骤、地点、时间和联系方式；
- 展示信息来源、发布日期及适用范围；
- 发现知识过期、冲突或证据不足时进行风险提示；
- 收集匿名化用户反馈，帮助团队持续改进知识库。

### 3. 一句话价值主张

> 让学生不必在多个网站和群聊中反复搜索，也能快速获得“有来源、可核验、能执行”的校园办事步骤。

### 4. 建设原则

1. **准确优先：** 不追求每个问题都回答，没有依据时主动拒答。
2. **先检索后生成：** 正式答案尽量依据知识库检索结果生成。
3. **来源可追溯：** 展示原始通知、发布部门、日期和适用范围。
4. **小范围做完整：** 第一版只支持4个高频事项，稳定后再扩展。
5. **隐私最小化：** 原型阶段不采集真实学号、身份证号和账号密码。
6. **结果结构化：** 不只输出大段文字，而是生成清晰的办事卡片。
7. **演示可复现：** 比赛提交的代码、配置和知识资料能够复现演示效果。

## 二、项目范围

### 1. 推荐支持的8项事务

| 编号 | 事务 | 优先级 | 选择原因 |
|---|---|---:|---|
| S01 | 学生证补办 | P0 | 流程清晰，适合现场演示 |
| S02 | 校园卡补办 | P0 | 高频且容易理解 |
| S03 | 宿舍报修 | P0 | 容易形成完整操作闭环 |
| S04 | 请假办理 | P0 | 能展示智能体主动追问能力 |
| S05 | 奖学金申请 | P1 | 能展示资格条件和截止时间 |
| S06 | 助学金申请 | P1 | 能展示隐私保护和风险提示 |
| S07 | 转专业咨询 | P1 | 能展示复杂条件整理能力 |
| S08 | 毕业手续 | P1 | 能展示多步骤任务清单 |

P0是最小可行版本必须完成的事项；P1只有在P0稳定后才开始开发。

### 2. 最小可行版本功能

- [ ] 用户可以输入自然语言问题；
- [ ] 系统能够识别对应办事事项；
- [ ] 系统从知识库检索相关依据；
- [ ] 系统以结构化卡片返回答案；
- [ ] 缺少关键信息时能够主动追问；
- [ ] 回答展示来源和更新时间；
- [ ] 无可靠依据时触发兜底回复；
- [ ] 用户可以评价“有帮助”或“没帮助”；
- [ ] 可以查看当前支持的事项；
- [ ] 至少准备40个可重复执行的测试问题。

### 3. 第一版明确不做

- 不代替学生登录教务系统；
- 不自动提交真实请假、报修或奖助申请；
- 不进行缴费等资金操作；
- 不抓取需要登录且未经授权的校园数据；
- 不保存身份证、银行卡、账号密码等敏感信息；
- 不自行训练大型语言模型；
- 不覆盖全校所有学院和所有事务；
- 不对医疗、心理、法律问题作专业判断。

### 4. 验收指标

| 指标 | 建议目标 | 测量方法 |
|---|---:|---|
| 已支持事项意图识别准确率 | 不低于90% | 使用40条标注问题测试 |
| 知识来源正确率 | 不低于95% | 人工核对引用来源 |
| 关键字段完整率 | 不低于90% | 检查条件、材料、步骤、地点、时间和来源 |
| 知识库外问题正确拒答率 | 不低于90% | 使用10条无依据问题测试 |
| 核心接口自动化测试 | 100%通过 | 执行后端和前端测试 |
| 典型回答时间 | 目标8秒以内 | 连续执行20次并记录 |
| 答辩演示稳定性 | 连续成功5次 | 按固定脚本重复操作 |

## 三、用户与典型场景

### 1. 目标用户

- 第一次办理校园事务的新生；
- 不熟悉学校部门分工的普通学生；
- 需要快速确认材料、地点和截止日期的学生；
- 经常帮助同学解答问题的班委和辅导员；
- 后续可以扩展到教职工和校园访客。

### 2. 核心用户故事

1. 作为学生，我想知道学生证丢失后需要准备什么，以免多次往返。
2. 作为学生，我想确认奖学金申请截止时间，并查看原始通知。
3. 作为学生，我只说“我要请假”时，系统应继续询问请假类型和时长。
4. 作为学生，当系统没有可靠资料时，我希望它明确告知不确定。
5. 作为知识维护者，我希望看到哪些问题经常回答失败，以便补充资料。

### 3. 推荐现场演示场景

#### 场景A：标准问题

用户输入：

```text
学生证丢了怎么补办？
```

系统展示事项名称、办理条件、材料、步骤、地点、时间、注意事项和信息来源。

#### 场景B：信息不完整

用户输入：

```text
我想请假。
```

系统追问请假类型、时长、是否离校等关键信息，然后给出对应流程。

#### 场景C：知识库外问题

用户输入：

```text
学校明年一定会新增哪些专业？
```

系统说明没有找到可靠依据，不编造专业名称，并给出建议咨询的部门。

## 五、技术架构

### 1. 推荐技术栈

| 层级 | 推荐方案 | 原因 |
|---|---|---|
| 前端 | Vue 3 + TypeScript + Vite + Element Plus | 学习资料多、组件丰富、适合快速开发 |
| 后端 | Python 3.12 + FastAPI + Pydantic | 代码清晰、自动生成接口文档、适合AI应用 |
| 数据库 | MySQL 8.x | 容易学习，适合结构化业务数据 |
| ORM和迁移 | SQLAlchemy 2 + Alembic | 管理数据模型和数据库版本 |
| 智能体 | 华为云AgentArts | 对应创新应用方向，支持知识库和工作流 |
| 知识能力 | AgentArts知识库 + RAG | 先检索校园资料，再生成回答 |
| 文件存储 | 原型期本地；云端可选OBS | 保存经过授权和脱敏的知识文件 |
| 测试 | Pytest + Vitest | 分别覆盖后端和前端 |
| 版本管理 | Git | 支持三人协作和版本回退 |
| 部署 | Docker Compose，后续可部署华为云ECS | 保证环境一致并便于复现 |

                        │ HTTPS / JSON
┌───────────────────────▼──────────────────────┐
│                FastAPI后端服务               │
│ 会话管理 │ 事项服务 │ Agent适配 │ 反馈 │ 日志 │

       ┌────────▼────────┐  ┌──────▼────────────────┐
       │      MySQL      │  │ 华为云AgentArts       │
       │ 事项/来源/反馈  │  │ 意图/知识检索/LLM     │
       └─────────────────┘  └──────┬────────────────┘

### 3. 为什么需要独立后端

- 云端访问凭证不能暴露在浏览器中；
- 后端可以统一校验用户输入和智能体输出；
- 后端可以补充来源元数据和兜底规则；
- 后端可以保存匿名化质量反馈；
- 云平台接口变化时只需修改适配层；
- 云服务异常时可以切换到演示用模拟服务。

### 4. 推荐智能体工作流

```text
开始
  ↓
输入清洗与安全检查
  ↓
意图识别
  ├─ 已支持事项 → 参数提取
  ├─ 信息不足 → 生成追问
  └─ 未支持事项 → 返回支持范围
  ↓
知识检索
  ↓
检索结果判断
  ├─ 有可靠依据 → 大模型生成结构化答案
  ├─ 来源过期/冲突 → 风险提示
  └─ 依据不足 → 拒绝编造并给出咨询建议
  ↓
输出格式校验
  ↓
结束
```

## 七、知识库设计

### 1. 知识条目模板

```markdown
# 学生证补办

- 事项编码：S01
- 来源名称：关于学生证补办工作的通知
- 来源部门：学生工作处
- 发布日期：2026-09-01
- 生效日期：2026-09-01
- 失效日期：2027-08-31
- 适用对象：全日制在校本科生
- 适用校区：主校区
- 审核状态：已核验
- 最后核验人：知识工程负责人
- 最后核验日期：2026-09-15

## 办理条件
学生证遗失、损坏或主要信息发生变更。

## 所需材料
1. 学生本人有效身份证明；
2. 学生证补办申请；
3. 符合要求的证件照片。

## 办理步骤
1. 在指定系统或线下窗口提交申请；
2. 等待学院或管理部门审核；
3. 按通知时间领取新证。

## 办理地点
以来源通知中的地点为准。

## 办理时间
以学校最新通知为准。

## 注意事项
不能确认的信息不得自行补充。
```

以上内容只是格式示例。正式知识必须替换为学校真实、公开并经过核验的信息。

### 2. 必要元数据

| 字段 | 必填 | 说明 |
|---|---:|---|
| item_code | 是 | 事项编码，如S01 |
| title | 是 | 事项名称 |
| source_title | 是 | 原始通知名称 |
| source_department | 是 | 发布部门 |
| source_url | 是 | 学校官方来源地址 |
| publish_date | 是 | 发布日期 |
| effective_from | 否 | 生效日期 |
| effective_to | 否 | 失效日期 |
| audience | 是 | 适用对象 |
| campus | 否 | 适用校区 |
| status | 是 | draft、verified、expired或conflict |
| reviewer | 是 | 核验负责人 |
| reviewed_at | 是 | 最后核验时间 |
| version | 是 | 知识版本号 |

### 3. 知识治理流程

```text
发现资料
→ 确认是否为官方公开来源
→ 保存原文和来源地址
→ 提取条件、材料、步骤、地点和时间
→ 第二名成员交叉核验
→ 标记为verified
→ 上传知识库
→ 执行命中测试
→ 正式使用
→ 按有效期定期复查
```

### 4. 知识冲突处理

1. 优先使用发布日期较新且仍然有效的官方通知；
2. 校级与院级通知存在差异时，按适用对象和范围分别保存；
3. 无法确认时将状态设为`conflict`；
4. 冲突知识不能生成确定结论；
5. 回复中提示用户联系责任部门确认；
6. 每周对冲突条目进行一次人工复核。

### 5. 检索策略

- 使用事项编码、校区、学生类型和有效期等标签缩小范围；
- 对口语化问题使用语义检索；
- 每次召回3至5个相关片段；
- 检索结果无可靠来源时触发拒答；
- 每个事项至少测试5种不同问法；
- 过期和冲突文档不得作为唯一正式依据。

## 十三、项目创新点

### 1. 从“能够回答”升级为“能够执行”

系统将长篇通知转换为条件、材料、步骤、地点、时间和下一步行动，减少学生理解和整理信息的成本。

### 2. 可信知识与来源追溯

回答基于经过核验的校园知识库，展示来源、日期、适用范围和知识状态；证据不足时拒绝编造。

### 3. 参数化主动追问

系统根据不同事项识别缺失参数，例如校区、年级、请假时长和学生类型，而不是一次输出大量不相关内容。

### 4. 知识生命周期管理

知识需要经历收集、核验、发布、更新、过期和冲突处理，而不是上传后永久不变。

### 5. 可扩展能力

后续可以扩展：

- 增加更多学院和校区；
- 增加语音输入和无障碍朗读；
- 生成个性化待办清单；
- 接入学校正式授权的业务接口；
- 为辅导员提供高频问题统计；
- 扩展到企业园区和政务办事场景。

## 二十、实施结论

项目应当优先完成以下可信闭环：

```text
真实问题
→ 正确识别事项
→ 检索经过核验的知识
→ 生成结构化步骤
→ 展示信息来源
→ 证据不足时拒答
→ 收集反馈并更新知识
```

成员一负责保证“知识正确”，成员二负责保证“用户会用”，成员三负责保证“系统能运行并且回答受控”。三人团队先将4个P0事项做到稳定、准确、可演示，再逐步加入P1事项。只要三条主线每周都产生可以检查的成果，项目就能逐渐形成一个可开发、可测试、可答辩和可扩展的完整作品。
