# 校园办事小秘书 · AgentArts 智能体工作流配置说明（v1.0）

> **用途**：在华为云 AgentArts（智果）控制台按本文搭建「校园办事小秘书」问答工作流；后端通过 `app/services/agentarts_client.py` 调用（见第 6 节）。
> **版本**：v1.0 ｜ **编制日期**：2026-10-16 ｜ **依据**：实施方案第 4 周「AgentArts 知识库和工作流」、第 5 周「后端实现 AgentArts 客户端适配层」
> **配套文档**：知识库文档 `docs/AgentArts知识库文档-学生事务核验版.md`；接口契约 `docs/api.md` §3.3（结构化办事卡片）。

---

## 1. 工作流目标与总体流程

**设计原则（与实施方案一致）**：

1. 先检索后生成：正式答案必须能对应到知识库检索结果；
2. 无可靠依据时明确拒答，不编造学校政策、时间、地点与联系方式；
3. 信息不足时主动追问，不猜测关键参数；
4. 统一 JSON 输出，与后端契约 `AnswerCard` 对齐；
5. 来源可追溯：答案展示来源、发布日期与适用范围。

**节点总览**：

```
[开始] 输入 question / context
   │
   ▼
[意图识别] 大模型节点：输出 intent ∈ {S01…S08, unknown}
   │
   ├─ unknown ──────────────▶ [结束] unsupported（暂不支持）
   ▼
[知识检索] 知识库节点：按事项检索，top_k = 5，输出 snippets[]
   │
   ▼
[依据判断] 条件分支
   ├─ 无有效依据（snippets 为空）────────▶ [结束] insufficient_evidence（拒答）
   ├─ 缺关键参数（S04 请假类型 / S05 奖学金类别）▶ [结束] need_clarification（追问）
   ▼
[大模型生成] 仅依据知识片段，输出统一 JSON
   │
   ▼
[结束] 输出 answer（统一 JSON 文本）
```

> 注：节点名称以控制台实际节点类型为准（大模型节点、知识库检索节点、条件分支、开始/结束节点）；条件表达式按平台语法书写，本文给出判定条件与示例。

---

## 2. 知识库准备（前置步骤）

1. 上传知识库文档 `docs/AgentArts知识库文档-学生事务核验版.md`：
   - 方式一（推荐先试）：整体上传一个文档，AgentArts 自动分块；
   - 方式二（若出现跨事项串扰）：按条目拆分为 8 个文档分别上传（各条目以 `## Sxx` 开头，切分边界清晰）。
2. 知识库命名建议：`campus-affairs-v2026.10`（与知识版本号一致，便于后续更新替换）。
3. 检索参数建议：top_k = 5（实施方案 §7.5：每次召回 3 至 5 个相关片段）；若平台支持元数据过滤，按 `item_code` 过滤事项。
4. 知识条目全部为「已核验」状态、有效期至 2027-08-31；到期前对照调研清单的 ⚠️ 时效项复查更新。

## 3. 节点配置

### 3.1 开始节点

| 输入变量 | 类型 | 必填 | 说明 |
|---|---|---|---|
| question | string | 是 | 学生问题原文（经输入清洗：去首尾空白、长度上限 500 字） |
| context | object | 否 | 上下文：campus（校区）、student_type（undergraduate / graduate 等） |

> 后端调用时 question 由 `POST /api/chat/messages` 的 message 透传（后端先做输入清洗与长度校验）。

### 3.2 意图识别节点（大模型节点）

**系统提示词**（直接粘贴到节点配置）：

```
你是校园事务意图识别器。根据学生问题判断所属事项，只输出一个 JSON 对象。

事项与常见问法关键词：
- S01 学生证补办：学生证
- S02 校园卡补办：校园卡、一卡通
- S03 宿舍报修：报修、维修、宿舍设施故障（水龙头、水管、灯、空调等）
- S04 请假办理：请假、事假、病假、公假
- S05 奖学金申请：奖学金
- S06 助学金申请：助学金、困难补助、助学贷款
- S07 转专业咨询：转专业
- S08 毕业手续：毕业、离校、学位证、毕业证

规则：
1. 只输出 {"intent": "Sxx"}，不要输出解释文字或 Markdown 代码块；
2. 同时命中多个事项或无法判断时，输出 {"intent": "unknown"}；
3. 同时命中多个事项且能从问题中区分时，正常输出对应事项；
4. 只依据问题文本判断，不要编造。
```

**输出规范**：`{"intent": "S01"}` ～ `{"intent": "S08"}` 或 `{"intent": "unknown"}`。

**分支**：`intent == "unknown"` → 结束节点输出 `{"status": "unsupported"}`（暂不支持，由后端提示用户换一种问法或联系责任部门）。

> 关键词表与后端 `app/services/intent.py` 的 `INTENT_KEYWORDS` 一致（后端规则路径为降级方案，两者输出同构）。

### 3.3 知识检索节点（知识库节点）

| 配置项 | 值 |
|---|---|
| 知识库 | 第 2 节准备的知识库（campus-affairs-v2026.10） |
| 检索问题 | 学生问题原文（question） |
| top_k | 5 |
| 事项过滤 | 若平台支持：按意图节点的 item_code 过滤；不支持则在生成提示词中限定 |
| 校区/学生类型过滤 | context.campus、context.student_type（无匹配时不收窄，避免误拒答） |

**输出**：snippets[]，每条含：标题、发布部门、发布日期、有效期、适用对象、正文（即知识条目的分块内容）。

### 3.4 依据判断节点（条件分支）

判定条件（按优先级）：

1. **无有效依据**：snippets 为空 → 拒答分支；
2. **缺关键参数**：意图为 S04 且问题中未出现「事假/病假/公假/假条/请假条/几天/小时/天」任一；或意图为 S05 且问题中未出现「国家奖学金/校级奖学金/院级奖学金/励志/一等/二等/三等」任一 → 追问分支；
3. 其余 → 大模型生成节点。

> 判定参数表与后端 `app/services/intent.py` 的 `CLARIFY_RULES` 一致；工作流与后端降级路径行为保持同构，便于切换与对照测试。

### 3.5 大模型生成节点

**系统提示词**（与后端 `app/services/chat_service.py` 的 `SYSTEM_PROMPT` 保持一致，保证工作流与后端降级路径输出同构）：

```
你是校园办事小秘书，只能依据给定的「知识片段」回答学生问题。

必须遵守：
1. 不得根据常识编造学校政策、时间、地点、材料和联系方式；
2. 知识片段不足以支撑完整回答时，只输出 {"status": "insufficient_evidence"}；
3. 用户信息不足时不要猜测，直接按依据不足处理；
4. 正式答案必须能对应到给定的知识片段；
5. 知识片段标注过期或冲突时不得输出确定结论；
6. 不索取身份证号、银行卡号、账号密码等敏感信息；
7. 使用简洁、可执行的步骤回答；
8. 只输出一个 JSON 对象，不要输出解释文字或 Markdown 代码块；
9. 只要知识片段包含该事项的办理条件、材料或步骤，就必须给出结构化回答，不得改判为依据不足；
10. 保持简洁：summary 不超过 60 字，eligibility / materials / steps 各不超过 5 条、每条不超过 40 字，
    contacts 不超过 2 条。

输出 JSON 结构：
{"title": "事项名称", "summary": "一句话概述", "eligibility": ["办理条件"],
 "materials": ["所需材料"], "steps": ["办理步骤"], "location": "办理地点或 null",
 "deadline": "YYYY-MM-DD 或 null", "contacts": ["联系方式"], "warnings": ["风险提示"]}
```

> **第 9、10 条为实测调优结论（2026-10-16）**：MaaS 直连路径实测发现，缺少第 9 条时模型会把
> 「片段有依据」的问题误判为 `insufficient_evidence`；缺少第 10 条时输出过长会使耗时从约 2 秒
> 涨到 30 秒以上，直接顶破契约的 8 秒前端超时。工作流侧同样建议保留这两条约束。

**用户输入模板**（由工作流组装，与后端 `_build_user_prompt` 同构）：

```
【事项】{意图节点输出的事项名称}
【校区】{context.campus，可选}
【学生类型】{context.student_type，可选}
【知识片段】
1. 标题：…｜发布部门：…｜发布日期：…｜有效期：…~…｜适用对象：…｜适用校区：…｜状态：…
   正文：…
（最多 5 条，按相关性排序）
【学生问题】{question}
```

**输出**：统一 JSON 文本（见第 5 节规范）。

### 3.6 结束节点

| 输出变量 | 类型 | 说明 |
|---|---|---|
| answer | string | 统一 JSON 文本（answered / insufficient_evidence / need_clarification / unsupported 四种状态之一） |

## 4. 拒答与追问分支

### 4.1 无依据拒答分支

- **触发条件**：知识检索节点返回 snippets 为空（含知识库未收录该事项、或全部条目已过期/冲突不可用）。
- **输出**：`{"status": "insufficient_evidence"}`。
- **行为约定**：不输出任何办事流程；后端向用户提示「暂未找到可靠的办理依据，请联系责任部门确认」，并回带「存在但不可用」的来源做风险提示（契约 §3.3）。

### 4.2 信息不足追问分支

- **触发条件**（与后端 CLARIFY_RULES 一致）：
  - S04 请假办理：未说明请假类型与时长参数；
  - S05 奖学金申请：未说明奖学金类别。
- **输出**：`{"status": "need_clarification", "clarifying_question": "…"}`。
- **追问问题**：
  - S04：你的请假类型是事假、病假还是公假？
  - S05：你想申请哪一类奖学金？

### 4.3 暂不支持分支

- **触发条件**：意图识别输出 unknown（知识库外问题或无法归属事项）。
- **输出**：`{"status": "unsupported"}`。
- **行为约定**：不编造答案；后端提示用户该问题暂不在服务范围内。

---

## 5. 统一 JSON 输出规范

工作流「结束节点」只输出**一个 JSON 对象**，四种状态：

| status | 结构 | 对应前端/契约状态 |
|---|---|---|
| answered | `{"title", "summary", "eligibility": [], "materials": [], "steps": [], "location", "deadline", "contacts": [], "warnings": []}` | answered（结构化办事卡片） |
| insufficient_evidence | `{"status": "insufficient_evidence"}` | insufficient_evidence（拒答） |
| need_clarification | `{"status": "need_clarification", "clarifying_question": "…"}` | need_clarification（追问） |
| unsupported | `{"status": "unsupported"}` | unsupported（暂不支持） |

**与后端契约 §3.3 的关系**：工作流输出的 JSON 是「答案本体」；后端在应答外层再包装 `status / intent / sources / conversation_id`（sources 由后端从数据库映射，不采信模型输出——契约 §1.2）。answered 卡片字段与 `AnswerCard` 一一对应，后端 `_parse_answer` 可直接解析。

## 6. 后端调用适配层

**实现**：`backend/app/services/agentarts_client.py`（`AgentArtsClient`，实现 `LLMClient` 协议）。

**当前接线（v1.0，生成委托模式）**：

- 后端保留「规则意图识别 + MySQL 可信检索」（已核验/有效期内/有正文三重过滤，检索逻辑在 `app/services/retrieval.py`），把系统提示词与知识片段交给 AgentArts 工作流执行生成；
- `get_llm_client()` 按优先级分流：**AGENTARTS_API_KEY + AGENTARTS_AGENT_ID 均配置 → AgentArts 工作流**；否则回退 MaaS 直连；再否则本地替身 / 生产明确失败（503）；
- 工作流在控制台仍按第 3 节六节点完整配置：其「大模型生成节点」即被后端调用的能力，「意图/检索/判断」节点的工作流内链路用于平台侧独立测试与演示，与后端降级路径输出同构、可对照验证。

**后续演进（可选）**：团队就绪后可将 `chat_service` 中段整体替换为工作流调用（只传 question，解析工作流返回的完整 JSON），后端只做校验、持久化与来源展示——因两端输出同构，切换时编排层改动集中在 `_run_pipeline` 一处。

**环境变量**（.env，不入库；样例见 .env.example）：

| 变量 | 说明 |
|---|---|
| AGENTARTS_API_KEY | 工作流调用凭证（控制台「凭证管理」申请） |
| AGENTARTS_AGENT_ID | 工作流（智能体）ID，控制台 AgentCard 页记录 |
| AGENTARTS_BASE_URL | 调用地址，以控制台该工作流「API 调用」页给出的值为准 |
| AGENTARTS_CONNECT_TIMEOUT | 连接超时（秒，缺省 2.0） |
| AGENTARTS_READ_TIMEOUT | 读取超时（秒，缺省 15.0） |
| AGENTARTS_MAX_ATTEMPTS | 超时/连接异常重试次数上限（缺省 2；4xx 与 429 不重试） |

**错误映射**（与契约 §4.5 一致）：超时 → 503 UPSTREAM_TIMEOUT；上游异常 → 503 UPSTREAM_ERROR；429 → 429 RATE_LIMITED。前端在异常时展示明确提示，不白屏。

## 7. 测试方案（全链路 20 条）

**问法构成**：8 个事项各 2 条（标准问法 + 口语/变体问法）+ 4 条知识库外问题。

| # | 事项 | 问法 | 期望 |
|---|---|---|---|
| 1 | S01 | 学生证丢了怎么补办？ | answered，来源为学生证补办条目 |
| 2 | S01 | 学生证坏了换新的要挂失吗？ | answered |
| 3 | S02 | 校园卡丢了怎么补办？ | answered |
| 4 | S02 | 一卡通找不到了咋办 | answered（一卡通同义） |
| 5 | S03 | 宿舍灯坏了找谁修？ | answered |
| 6 | S03 | 水龙头漏水怎么报修 | answered |
| 7 | S04 | 我要请假，需要办哪些手续？ | need_clarification（未说明类型） |
| 8 | S04 | 病假三天怎么请？ | answered |
| 9 | S05 | 奖学金申请需要准备哪些材料？ | need_clarification（未说明类别） |
| 10 | S05 | 国家奖学金大二能申请吗？ | answered |
| 11 | S06 | 助学金申请需要满足什么条件？ | answered |
| 12 | S06 | 家里困难想申请补助怎么办 | answered |
| 13 | S07 | 转专业需要满足哪些条件？ | answered |
| 14 | S07 | 大二想换专业，什么时候申请 | answered |
| 15 | S08 | 毕业手续要办哪些事项？ | answered |
| 16 | S08 | 离校手续在哪里查进度？ | answered |
| 17 | 库外 | 食堂几点开门？ | unsupported（不编造） |
| 18 | 库外 | 图书馆借书超期怎么办？ | unsupported |
| 19 | 库外 | 怎么选课？ | unsupported |
| 20 | 库外 | 明年学校一定会新增什么专业？ | unsupported |

**验收标准**（实施方案第 4 周）：
- 20 条问题中至少 18 条识别到正确事项（≥90%）；
- 正式答案能够显示正确来源（标题、部门、发布日期与知识条目一致）；
- 知识库外问题不生成虚假流程。

**执行记录**：每条测试记录「意图、召回文档、输出、失败原因」四列（对应知识库文档附录的更全量问法集：每事项 5 种问法）。
