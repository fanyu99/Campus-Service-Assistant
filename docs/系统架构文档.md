# 校园办事小秘书 · 系统架构文档

> 版本：v1.0 ｜ 编制日期：2026-10-16  ｜ 关联图：[系统总体架构图.html](./系统总体架构图.html)

## 1. 文档目的

本文描述“校园办事小秘书”当前代码实现对应的系统架构，帮助开发、测试、部署和答辩人员理解各层职责、数据流向和运行边界。

系统的核心目标是：让学生用自然语言咨询校园办事事项，系统只依据已核验、有效期内的知识回答，并以结构化卡片返回办理条件、材料、步骤、地点、期限、联系方式和风险提示。

## 2. 架构总览

系统采用前后端分离与容器化部署：

| 层次 | 主要组成 | 职责 |
| --- | --- | --- |
| 用户交互层 | Vue 3、Vue Router、TypeScript、Vite | 页面展示、输入问题、显示回答卡片、历史记录、反馈、设置 |
| Web 边缘层 | Nginx | 提供前端静态资源，把 `/api` 请求转发给后端 |
| 应用服务层 | FastAPI、Pydantic、SQLAlchemy | 接口路由、参数校验、会话隔离、业务编排、统一错误响应 |
| 问答领域层 | 意图识别、闲聊分类、知识检索、LLM Client、输出校验 | 把自然语言问题转换成安全、可验证的结构化回答 |
| 持久化层 | MySQL 8、Alembic | 保存事项、来源文档、会话、消息和反馈；迁移管理数据库结构 |
| 外部模型层 | AgentArts 或华为云 MaaS | 执行工作流或生成模型回答；后端负责超时、重试和错误归类 |
| 运行与运维层 | Docker Compose、健康检查、数据卷、知识导入脚本 | 统一启动顺序、数据库初始化、知识导入和运行维护 |

## 3. 关键组件

### 3.1 前端

前端位于 `frontend/src`，采用 Vue 3 单页应用。

- `App.vue`：应用壳、全局布局和主题相关能力。
- `views/`：首页、聊天、历史、事项、帮助和设置页面。
- `components/AnswerCard.vue`：展示结构化回答。
- `components/SourceList.vue`：展示模型回答所依据的来源。
- `api/client.ts`：集中封装后端 API 请求。
- `composables/useProfile.ts`：维护匿名会话标识和用户侧配置。
- `styles/theme.css`：项目视觉主题、字体、颜色和动效。

前端不直接访问数据库或模型服务，所有业务数据通过后端 API 获取。

### 3.2 Nginx

生产部署中，前端容器使用 Nginx：

1. 返回 Vite 构建产物。
2. 将 `/api/*` 请求代理到 backend 容器的 8000 端口。
3. 对外暴露 80 端口。
4. 通过 `depends_on: backend: service_healthy` 确保后端健康后再启动前端。

### 3.3 FastAPI 应用

后端入口是 `backend/app/main.py`。应用创建时注册以下路由：

| 路由模块 | 主要接口能力 |
| --- | --- |
| `health.py` | 健康检查 |
| `service_items.py` | 查询校园办事项及展示字段 |
| `chat.py` | 发送问题并获得结构化回答 |
| `conversations.py` | 查询会话和历史记录 |
| `feedback.py` | 提交回答反馈 |
| `knowledge.py` | 查询知识来源及核验状态 |

应用启动时创建进程内滑动窗口限流器，并注册统一异常处理。生产环境配置由 `Settings` 从根目录 `.env` 和容器环境变量读取。

## 4. 核心问答链路

一次正常问答按以下顺序执行：

1. 前端提交 `POST /api/chat/messages`，携带问题、可选的 `conversation_id` 和会话标识。
2. 后端校验消息长度、会话标识和请求格式；敏感数据与提示词注入由输入清洗逻辑拒绝。
3. 根据会话历史识别事项意图，并处理闲聊、追问、需要澄清和暂不支持等情况。
4. 按事项代码检索知识来源，过滤未核验、过期、缺少正文或冲突的资料。
5. 若证据不足，直接返回 `insufficient_evidence`；若存在冲突，返回 `conflict`，避免模型自行猜测。
6. 若证据充分，调用 AgentArts 工作流或 MaaS 模型生成 JSON。
7. 后端解析模型返回，校验结构化字段、长度和状态，不能把模型原始来源当作可信来源。
8. 后端从数据库映射真实来源，和回答一起写入会话与消息明细。
9. 前端按状态显示回答卡片、澄清问题、拒答提示、错误提示或重试入口。

核心编排位于 `backend/app/services/chat_service.py`。它把“输入清洗 → 意图识别 → 知识检索 → 依据判断 → 模型生成 → 输出校验”组织成一条事务边界清晰的流水线。

## 5. 模型接入策略

后端通过 `backend/app/services/llm_client.py` 统一模型调用接口，业务编排不依赖某一个供应商。

### AgentArts 工作流

当 `AGENTARTS_API_KEY`、`AGENTARTS_BASE_URL` 和 `AGENTARTS_AGENT_ID` 配置完整时，优先调用 AgentArts 工作流。工作流可以承载更复杂的智能体节点，但必须保持后端 API 的入参和出参契约不变。

### MaaS 模型服务

未启用 AgentArts 时，可以通过 `MAAS_API_KEY` 调用兼容 OpenAI 风格接口的 MaaS 模型。模型、连接超时、读取超时、最大 token 数和是否关闭思考链均由配置控制。

外部模型失败时，后端将连接失败、超时、上游错误和无效 JSON 转换成稳定的业务状态，前端不需要理解供应商的原始错误格式。

## 6. 数据设计

当前主要数据对象如下：

| 数据对象 | 作用 | 典型内容 |
| --- | --- | --- |
| `service_items` | 校园办事项 | 事项代码、标题、分类、图标、展示色调、提示语 |
| `source_documents` | 知识来源 | 来源标题、链接、正文、核验状态、有效期、版本 |
| `conversations` | 会话摘要 | 会话 ID、匿名会话标识、最近意图、最近状态、时间 |
| `conversation_messages` | 消息明细 | 学生问题、助手回答、角色、时间、结构化内容 |
| `feedback` | 用户反馈 | 会话、评价、补充意见和时间 |

会话与消息在同一个数据库事务中保存。一次问答通常写入一条学生消息和一条助手消息；失败时避免产生只有半条消息的会话记录。

匿名会话通过 `X-Session-Token` 进行隔离。继续访问会话时，如果标识不一致，后端返回“会话不存在或已过期”，防止不同用户跨标识读取或续写会话。

## 7. 安全与可靠性

### 输入安全

- 限制单条消息长度。
- 拒绝身份证号、手机号、银行卡号、密码和其他敏感凭据的输入。
- 拒绝提示词注入特征。
- 来源 URL 只接受 HTTP(S) 绝对地址。

### 内容安全

- 模型只能依据后端提供的知识片段回答。
- 没有足够证据时拒答。
- 知识冲突或过期时不输出确定结论。
- `sources` 由后端从数据库映射，不信任模型自行生成的来源。

### 运行可靠性

- 后端容器启动前循环执行 `alembic upgrade head`，数据库未就绪时等待重试。
- Docker Compose 使用数据库健康检查作为后端启动条件。
- 模型调用设置连接超时、读取超时和有限次数重试。
- API 返回稳定的业务状态，前端可针对超时、限流和上游错误给出明确提示。

## 8. 部署架构

生产环境由 `docker-compose.yml` 管理三个容器：

```text
frontend :80  →  backend :8000  →  db :3306
                              ↘  AgentArts / MaaS
```

- `frontend`：构建并托管前端资源。
- `backend`：执行迁移后启动 Uvicorn。
- `db`：MySQL 8，使用 `db-data` 卷保存数据，宿主机只通过 `127.0.0.1:3306` 访问。
- `.env`：保存数据库口令和模型服务密钥，不应提交到版本库。

首次部署后，需要按顺序运行演示事项导入、真实知识导入和展示字段回填脚本。知识未导入时，系统按安全默认返回依据不足，而不是生成占位答案。

## 9. 当前架构边界与演进方向

当前系统适合单体后端、单数据库和小规模并发场景。进程内限流器在多副本部署时会按副本分别计数，若需要全局限流，应替换为 Redis 等共享计数方案。

后续可以沿着以下方向演进：

1. 将知识检索抽象为独立的检索适配层，接入全文检索或向量检索。
2. 把模型调用指标、超时率和拒答率接入统一监控。
3. 为知识来源增加后台审核和版本发布流程。
4. 在多副本部署前引入共享限流、集中日志和任务队列。
5. 将 AgentArts 工作流配置和后端契约纳入版本化验收。
